## 📑 CLI UX 개선 디자인 브리프: 엔터프라이즈 모니터링 시스템 구축

현재 CLI는 기능 실행에 초점을 맞추고 있어, 사용자가 **'현재 시스템이 어떤 상태에 있는지'**를 직관적으로 파악하기 어렵습니다. 데이터 마이그레이션과 같은 복잡하고 위험도가 높은 프로세스에서는 단순한 로그 기록을 넘어, **'실시간 모니터링(Monitoring)'** 경험을 제공해야 합니다.

본 브리프는 기존의 단순 출력(Plain Text Print)을 **'프로세스 모니터링 텍스트 UI(Text UI)'**로 업그레이드하는 것을 목표로 하며, 실패 시에는 단순 오류 메시지 전달이 아닌, **진단 가능한 정보**를 제공하여 운영자(Operator)의 대응 시간을 최소화하는 데 중점을 둡니다.

---

### 1. ⚙️ 핵심 디자인 원칙 및 톤앤매너

*   **원칙 1: 모니터링 중심 (Monitoring Focus):** 모든 과정은 '실행'이 아닌 '상태 변화'로 인식되어야 합니다.
*   **원칙 2: 시각적 계층 구조 (Visual Hierarchy):** 성공, 경고, 실패 메시지는 명확한 색상 및 박스 구조로 분리되어야 합니다.
*   **원칙 3: 정보의 구조화 (Structured Information):** 실패 메시지는 반드시 '무엇이(What)', '왜(Why)', '어떻게(How)' 실패했는지에 대한 구조를 가져야 합니다.

### 2. 🎨 개선된 텍스트 UI 요소 정의 (코드 구현 가이드)

기존의 `print_header`, `print_step`, `print_ok`, `print_fail` 함수를 다음과 같은 전문적인 모니터링 함수로 대체해야 합니다.

#### 2.1. 🚀 `print_header(title, subtitle)`
*   **기능:** 대규모 프로세스 시작을 알림.
*   **시각적 특징:** 상단 경계선, 강조된 색상, 시스템 시작 느낌.
*   **출력 예시:**
    ```
    ============================================================
    🚀 ORACLE MIGRATION PIPELINE START
    [Subtitle] 목표: Source DB를 Target DB로 안전하게 전환합니다.
    ============================================================
    ```

#### 2.2. 📈 `print_step(step_id, title, total_steps)`
*   **기능:** 전체 파이프라인 중 현재 위치와 진행률을 표시합니다.
*   **시각적 특징:** Step ID와 함께, 전체 진행률을 시각화합니다.
*   **출력 예시:**
    ```
    [STEP 3/8] Export (exp/expdp) 진행 중...
    [Progress:#####################-----] 70% 완료 (120/171 records processed)
    ```

#### 2.3. 🔄 `print_progress(current, total, message)`
*   **기능:** 반복문(Loop)이나 데이터 처리 과정 중의 진행 상황을 표시합니다. (핵심 기능)
*   **구현 기법:** `\r` (Carriage Return)을 사용하여 현재 줄을 덮어쓰며 업데이트합니다.
*   **출력 예시 (실시간 업데이트):**
    ```
    > 데이터 처리 중... [#####-----] 55% (2,200 / 4,000 레코드)
    ```

#### 2.4. ✅ `print_ok(message)`
*   **기능:** 단계 또는 프로세스 완료 성공.
*   **시각적 특징:** 녹색 강조, 완료 메시지 명확화.
*   **출력 예시:**
    ```
    ✅ [SUCCESS] Step 3: Export 완료. 덤프 파일이 성공적으로 생성되었습니다.
    ```

#### 2.5. 🚨 `print_fail(step_id, step_name, error_message, diagnostic_details)` (최대 개선 영역)
*   **기능:** 실패를 알리고, 사용자가 즉시 대응할 수 있는 구조화된 진단 정보를 제공합니다.
*   **시각적 특징:** 빨간색 강조, 명확한 경계 박스, 계층적 정보 제공.
*   **출력 예시:** (아래 3번 참고)

### 3. 💀 표준화된 실패 보고서 포맷 (Diagnostic Code)

실패 시, 사용자에게는 **'쉬운 해석'**을, 개발자에게는 **'기술적 정보'**를 제공해야 합니다. 다음 구조를 표준으로 사용합니다.

**[🚨 FATAL ERROR DETECTED]**
*   **Failure Step:** Step N: [단계 이름]
*   **Reason (User View):** [간단하고 사용자 친화적인 실패 원인 요약]
*   **Diagnostic Code:** `MIG-[단계 ID]-[랜덤 식별자]` (예: `MIG-03-D4F7E`)
*   **Technical Cause (Dev View):**
    *   **Exception:** `[Exception Type]`
    *   **Message:** `[원래의 에러 메시지 전문]`
    *   **Source:** `[에러가 발생한 코드 파일 및 라인 번호]`
*   **Mitigation Action (Next Step):**
    1.  **DB 체크:** Source DB의 사용자 권한을 재확인하십시오.
    2.  **Config 체크:** `migration_config.yaml` 파일의 접속 비밀번호가 만료되지 않았는지 확인하십시오.
    3.  **로그 참조:** 상세 내용은 `[로그 파일명]`을 참조하십시오.
